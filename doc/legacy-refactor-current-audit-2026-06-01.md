# Отчет: что осталось от старого подхода и что рефакторить дальше

Дата анализа: 2026-06-02

Область анализа: `_core`, `_project`, `htdocs`, `cli`; без `vendor` и `legacy_assets`.

## Краткий вывод

Проект уже в основном переведен от старого service-locator / procedural runtime подхода к DI: legacy gateway-вызовы, `::instance()`, `parse_ini_file()`, `call_user_func*` и `eval()` в production-срезе не найдены. Leaf-level self-default в upload-size-limit блоках закрыт: provider теперь получает runtime settings через container/block dependency chain. `safe_serializer` и `image_metadata_reader` больше не создают `warning_capture` сами: capture приходит из composition root. `image_modify` и spec-file image row больше не создают `image_metadata_reader` как скрытый fallback. ADOdb session environment больше не создает loader/globals adapters сам, а ADOdb database-session engine требует injected environment. Base service, form, cookie, image modify services, user service, loader view router, meta maker и spec-file image row больше не создают свои state сами: они требуют state из composition/runtime root. `file_data/row`, `cache/file`, `cache`, `template`, `log/parser_base`, `log/parser_bootstrap`, `translation`, `file_system`, config source checks, entity filesystem discovery, entity-description cache IO, model request SQL IO, meta maker, tab alias checks, soap wsdl checks, debug parent-meta checks, block template/debug checks, root HTML asset/template checks, bootstrap error logger, bootstrap entrypoint, bootstrap loader, installer `check_directories`, installer `fan_version`, project-tool `conv_entity` / `create_entity` / `upgrade_blocks` / `entity_filter` / `db_up`, log-viewer header, CLI installer, plain image controller, plain db-file controller, matcher route checks, image source checks, plain email template checks и error demonstrator template/data checks больше не вызывают filesystem/output native-функции напрямую: IO идет через injected `file_data_storage`, `cache_file_storage`, `cache_source_file_metadata`, `config_source_file_storage`, `model_request_file_storage`, `meta_file_storage`, `template_file_storage`, `log_file_storage`, `translation_file_storage`, `file_system_storage`, `entity_file_discovery`, `entity_description_file_storage`, `block_file_storage`, `root_html_file_storage`, `error_logger_file_storage`, `bootstrap_loader_file_storage`, `installer_filesystem_operations`, `project_tool_file_storage`, `cli_install_file_storage`, `plain_file_storage`, `matcher_route_file_storage`, `image_source_file_storage`, `tab_alias_file_storage`, `soap_wsdl_file_storage`, `email_template_file_storage` и `error_demonstrator_file_storage`. Native PHP session calls теперь также изолированы в injected `native_session`. Главный оставшийся долг теперь в static compatibility facades, большом central composition root, ручном include/require слое и явных environment/native adapters.

## Таблица оставшегося рефакторинга

| Приоритет | Участок | Что осталось от старого подхода | Примеры файлов | Риск | Что сделать дальше |
|---:|---|---|---|---|---|
| 1 | Static bootstrap lifecycle | `bootstrap` все еще главный static facade и держит static `$contextState`. Большая часть state graph уже вынесена в объекты, но lifecycle по-прежнему стартует через static API. | `_core/bootstrap.php`, `_core/bootstrap/context_registry_state.php`, `_core/factory/bootstrap/context_factory.php`, `_core/bootstrap/state.php`, `_core/bootstrap/runner.php` | Средний | Выделить non-static application/bootstrap runner; static `bootstrap` оставить compatibility-оболочкой для `htdocs`, CLI и exception fallback. |
| 2 | Static container registry bridge | `container_registry` уже тонкий, но все еще static мост к container state. Это удобно для legacy compatibility, но normal runtime лучше вести через явный context/container. | `_core/di/container_registry.php`, `_core/di/container_registry_state.php`, `_core/factory/bootstrap/context_container_factory.php`, `_core/bootstrap/container_registry_state_factory.php` | Средний | Сужать API static registry, убирать новые зависимости от `container_registry`, передавать container/context явно через bootstrap/application objects. |
| 3 | Central composition root | `application_container_factory` содержит десятки `default*Factory()` helpers и знает почти обо всех сервисах. Это лучше hidden defaults в leaf-классах, но класс стал слишком крупным root-ом. | `_core/factory/application_container_factory.php` | Средний | Разбить на smaller composition roots: bootstrap/runtime, IO adapters, service factories, model/entity, block/template. Публичные container keys лучше сохранить на первом шаге. |
| 4 | Dynamic configured construction | Dynamic construction ограничен одним explicit boundary, но internal/core services еще частично проходят через строковые class names и config/meta-driven factories. | `_core/factory/configured_service_factory.php`, `_core/di/*_factory.php`, `_core/service/template/*`, `_core/block/**/*.meta.php` | Низкий-средний | Разделить internal typed factory map и plugin/config extension API; `new $className` оставить только для настоящих extension points. |

| 6 | Request/session environment | Superglobals вынесены вниз, но модель окружения все еще mutable/procedural через `$GLOBALS`, `$_SERVER`, session globals. | `_core/adapter/request_input_globals.php`, `_core/adapter/adodb_session_globals.php`, `_core/service/request.php` | Средний | Выше adapter-уровня передавать request/session context objects; `$GLOBALS` оставить только в самом нижнем compatibility adapter. |

## Рекомендуемый порядок

| Шаг | Работа | Почему сейчас |
|---:|---|---|
| 1 | Вынести bootstrap/exception low-level fallback-и | После переноса bootstrap runtime, CLI installer, web-installer, compiled-template loader и ADOdb defaults в explicit factories/composition root это основной оставшийся self-default слой. |
| 2 | Закрепить installer/bootstrap runtime source guards | Runtime и installer стали consumers injected dependencies; важно не вернуть lazy construction. |
| 3 | Сужать `container_registry` и `bootstrap` static facades | После leaf-level cleanup главный долг остается в lifecycle compatibility bridge. |
| 4 | Разбить `application_container_factory` | Сейчас туда стянуты правильные defaults, но class слишком крупный; дробить стоит после стабилизации static lifecycle. |
| 5 | Разделить typed internal factories и config/plugin extension boundary | После cleanup native IO можно точнее ограничить строково-динамическое создание объектов. |
